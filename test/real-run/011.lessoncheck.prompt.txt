## Two kinds of number

Python has two main number types. An `int` such as `3` is a whole number and is exact, however large it gets. A `float` such as `3.0` or `0.1` has a fractional part and is only stored approximately; that is what this lesson is about. Writing a decimal point makes a float, so `3` and `3.0` are different types.

```python
print(type(3), type(3.0))
print(6 / 3, 7 // 2, 7 % 2, 1 + 0.5)
```

Output:
```
<class 'int'> <class 'float'>
2.0 3 1 1.5
```

`/` always gives a float, `//` gives the whole-number quotient, `%` gives the remainder, and an int combined with a float gives a float. That is all you need from numbers here.

## The surprise: 0.1 + 0.2

In machine learning almost every number you handle is a float, so it is worth seeing early that float arithmetic can look wrong.

```python
print(0.1 + 0.2)
print(0.1 + 0.2 == 0.3)
print((0.1 + 0.2) - 0.3)
print(1 + 2 == 3)
```

Output:
```
0.30000000000000004
False
5.551115123125783e-17
True
```

The sum is not exactly `0.3`, and the gap is tiny but not zero. `e-17` means "times 10 to the power of minus 17", so the gap is about 0.0000000000000000555. The same integers add exactly (`1 + 2 == 3` is `True`) because ints are exact.

This is not a bug in your code, and Python is doing what it was designed to do. You get the same answer in JavaScript, Java, C and most other languages, because they all use the same standard for floats, IEEE 754 "double precision" (64 bits). CPython uses the C `double` of the machine, which on essentially all current computers follows that standard. You can check this yourself in any other language you have installed.

## Why: binary can't store 0.1 exactly

The explanation takes three steps.

**Step 1: decimal has the same problem.** In decimal, 1/3 is 0.3333... and never ends, so any written-down version is slightly off. That is a limit of the number system, not of the person writing.

**Step 2: a computer counts in binary.** A float is stored with binary place values: 1/2, 1/4, 1/8, 1/16 and so on. A fraction can be written exactly only if its denominator, in lowest terms, is a power of 2. So 0.5 (1/2), 0.25 (1/4) and 0.375 (3/8) are exact. But 0.1 is 1/10, and 10 is not a power of 2, so in binary it repeats forever, like 0.0001100110011... It has to be cut off after a fixed number of bits (a 64-bit float keeps 53 significant bits).

**Step 3: the stored number is the nearest one that fits.** For 0.1 that is a number slightly above 0.1.

Why does `print(0.1)` show a clean `0.1`, then? Python prints the *shortest text that turns back into the same float*, not the full stored value. The display hides the error. To see the real value we can use `Decimal`, a number type from the `decimal` module of the standard library. Importing makes a tool from another module available in your program. `Decimal(0.1)` simply shows the exact value of the float it was given.

```python
from decimal import Decimal

print(0.1)
print(Decimal(0.1))
print(Decimal(0.5))
print(format(0.1, '.20f'))
print(0.5 + 0.25 == 0.75)
```

Output:
```
0.1
0.1000000000000000055511151231257827021181583404541015625
0.5
0.10000000000000000555
True
```

`format(x, '.20f')` asks for 20 digits after the point. `0.5` is exact, and so is the sum `0.5 + 0.25`, because both are sums of powers of 2. So the problem is not "all floats are wrong": it affects values that are not sums of powers of 2.

Now the three numbers behind `0.1 + 0.2 == 0.3`:

```python
print(Decimal(0.2))
print(Decimal(0.3))
print(Decimal(0.1 + 0.2))
```

Output:
```
0.200000000000000011102230246251565404236316680908203125
0.299999999999999988897769753748434595763683319641876220703125
0.3000000000000000444089209850062616169452667236328125
```

Stored `0.1` is about 5.55e-18 too big, stored `0.2` is about twice that too big (1.11e-17), and the sum of those two errors does not land on the float nearest to `0.3`. The exact sum falls between two neighbouring floats, and the result is the upper one: the stored `0.3` is slightly below 0.3, the stored sum slightly above, one float step apart. That step is the 5.55e-17 you saw as the difference earlier.

## Errors add up

The tiny error is not a one-off. Repeating an operation lets it build up. The loop below means "repeat this 10 times" (`_` is just a name for a counter we do not need), and `total += 0.1` means "add 0.1 to total".

```python
total = 0.0
for _ in range(10):
    total += 0.1
print(total)
print(total == 1.0)
print(abs(total - 1.0))
```

Output:
```
0.9999999999999999
False
1.1102230246251565e-16
```

Errors can grow or can cancel, and how large they get depends on the numbers and on the order of the operations. Here the result is almost right (off by about 1e-16) but not bit-for-bit equal to `1.0`. That is why a test like `total == 1.0` is fragile.

## Comparing floats safely

Replace `==` with "close enough". By hand: `abs(a - b) < tolerance`, where `abs` gives the size of a number ignoring its sign, and the tolerance is a small number you choose (`1e-9` is scientific notation for 0.000000001). The standard library has the same idea built in as `math.isclose`; `math` is a module you must import.

```python
import math

print(0.1 + 0.2 == 0.3)
print(abs((0.1 + 0.2) - 0.3) < 1e-9)
print(math.isclose(0.1 + 0.2, 0.3))
```

Output:
```
False
True
True
```

`isclose` uses a *relative* tolerance. Being off by 0.001 is huge for values near 0.001 but invisible for values near a billion. By default `isclose` allows a difference of up to 1e-09 times the larger of the two values (`rel_tol=1e-09`):

```python
print(math.isclose(0.001, 0.0015))
print(math.isclose(1e9, 1e9 + 0.5))
```

Output:
```
False
True
```

Both pairs differ by 0.0005 and 0.5, but only the second is small compared with its size. This explains an edge case that surprises people. When one value is 0, "a billionth of the bigger value" is a billionth of almost nothing:

```python
print(math.isclose(1e-12, 0.0))
print(math.isclose(1e-12, 0.0, abs_tol=1e-9))
```

Output:
```
False
True
```

Near zero you must supply `abs_tol`, a fixed allowed gap. The right tolerance depends on the problem and there is no universal number; the defaults suit roughly 9 digits of agreement. You can check the exact defaults yourself with `help(math.isclose)` and in the Python documentation for the `math` module.

## Rounding is for display

Keep two ideas apart: what is *stored* and what is *shown*. An f-string puts a value into text, and `:.2f` inside it means "a float with 2 digits after the point". `round(x, 2)` returns a new float rounded to 2 places. (f-strings get their own point in this topic.)

```python
x = 0.1 + 0.2
print(x)
print(f'{x:.2f}')
print(round(x, 2))
print(x == 0.3)
print(round(x, 2) == 0.3)
```

Output:
```
0.30000000000000004
0.30
0.3
False
True
```

The f-string only changes the text; `x` itself is unchanged, so it still fails `== 0.3`. `round` makes a new float, which is itself only the nearest float to a decimal, so `round(x, 2) == 0.3` happens to work here. It is not a general substitute for a tolerance.

Rounding also has a surprise that reveals the mechanism:

```python
print(round(2.675, 2))
print(format(2.675, '.20f'))
```

Output:
```
2.67
2.67499999999999982236
```

School rounding would give 2.68, but the float written `2.675` is stored just below 2.675 (the digits begin 2.67499999...), so it is not a tie at all and rounds down. Nothing is broken.

A separate, genuine rule: when a value is exactly a tie, Python 3's `round()` rounds to the nearest *even* number, called banker's rounding. This is documented behaviour and you can read it in `help(round)`.

```python
print(round(0.5), round(1.5), round(2.5), round(3.5))
```

Output:
```
0 2 2 4
```

## Which tool for which job

- Comparing two computed floats: use a tolerance, `math.isclose` (later `numpy.isclose` / `numpy.allclose` for arrays).
- Showing a number to a reader: use an f-string or `round()`.
- A value that must stay exactly decimal, money being the usual case: use whole numbers of cents, or the `Decimal` type, which you can look up later.

`==` on floats is fine for a value you set directly with no arithmetic in between, and for exactly representable values. When the numbers come out of calculations, it is safer to make the tolerance habit automatic.

### What a 64-bit float is made of

A 64-bit float is one sign bit, 11 exponent bits and 52 stored fraction bits (with an implied leading 1, which gives the 53 significant bits mentioned above). It works like scientific notation in binary. I am certain of this layout and of the epsilon value below; you can check them in the Python tutorial section "Floating-Point Arithmetic: Issues and Limitations" and in the documentation for the `sys` module. You can observe the bits yourself:

```python
import sys

print((0.1).hex())
print(sys.float_info.epsilon)
```

Output:
```
0x1.999999999999ap-4
2.220446049250313e-16
```

`hex()` shows the stored number in base 16: `1.999999999999a` times 2 to the power of -4. The repeating `1001` pattern of 0.1 in binary appears as `999...`, cut off and rounded up to `a` at the end. `epsilon` is the gap between `1.0` and the next float.

### Big numbers and the order of addition

The gap between neighbouring floats grows with the size of the number. A float has about 15 to 17 significant decimal digits, so beyond 2**53 (about 9.0e15) a float can no longer tell consecutive whole numbers apart. Ints do not have this limit: Python ints have no fixed size.

```python
print(2.0**53)
print(2.0**53 + 1 == 2.0**53)
print(2**53 + 1)
```

Output:
```
9007199254740992.0
True
9007199254740993
```

Float addition is also not always associative: the order of summing can change the last digits. `math.fsum` sums more accurately than a plain `sum`.

```python
print((0.1 + 0.2) + 0.3)
print(0.1 + (0.2 + 0.3))
print(sum([0.1] * 10))
print(math.fsum([0.1] * 10))
```

Output:
```
0.6000000000000001
0.6
0.9999999999999999
1.0
```

Two related things you will meet later: `float32`, used by many ML libraries, keeps far fewer digits than Python's float (about 7 decimal digits instead of 15 to 17), and `nan` (not a number) breaks `==` in a different way, since `nan == nan` is `False`. That is the next point in this topic.

Teaching standards. They hold for every subject. The illustrations come from Python; they show the standard and are not content to reuse. Use your own judgement about how to meet them.
- Depth. Aim for understanding the learner could rebuild on their own: why it works, not only what to do.
- Surprises. A surprising case is worth showing when explaining it reveals how Python works underneath, as in a = [1, 2]; b = a; b.append(3); print(a) prints [1, 2, 3], even though the code never touched a. Assignment in Python never copies anything. It makes a name refer to an object, so a and b are two names for the same list, and changing the list through one name shows through the other. The same rule explains why a function can change a list you pass to it, and why a pandas DataFrame or NumPy slice you 'copied' with = changes the original.. A mistake that reveals nothing, such as a slip (Forgetting the colon after an if or for line, typing pirnt instead of print, a missing closing parenthesis, writing from sklearn.linear_model import LinearRegresion, or misspelling a column name like df['prcie'].) or a wrong idea no reasonable learner holds, teaches nothing, so leave it out. Don't claim how common a mistake is: there is no data on that.
- Honest scope. When a rule has exceptions, say where it holds rather than stating it as absolute.
- Extensions go down, not sideways. After the lesson, the most valuable extension usually explains what happens underneath: the steps actually taken, what the idea is built on, why it behaves the way it does, and how the learner can observe that for themselves (Run the code and print things: type(x) and id(x) show what an object is and whether two names share it, a is b tests sameness, and help(obj) or dir(obj) lists what it can do. For data, print df.shape, df.dtypes, df.head() and df.isna().sum() after every step. For models, print the fitted attributes such as model.coef_ or model.classes_. The key habit is to change one thing, run it again and compare the output.). A tour of more uses or later topics only adds breadth the learner will meet in later lessons anyway. Explain an extension properly or leave it out: concrete and exact, like a good reference entry, never a passing hint such as "a clearer way comes later". Under the hood, be exact about what you know, say plainly where your certainty ends, and say where it can be checked. The learner doesn't have to master it.
- New things. If you use something the learner hasn't learned, explain it briefly where it appears.
- Honest about yourself. You are an AI teaching without a textbook in front of you. Where a claim is one you are less sure of, or one that experts dispute, say so plainly and say where it can be checked.
